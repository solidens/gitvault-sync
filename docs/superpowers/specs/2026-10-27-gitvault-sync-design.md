# Gitvault Sync — дизайн

Дата: 2026-10-27. Рабочее название, id плагина `gitvault-sync` (меняется в одном месте — `manifest.json`).

## Зачем

Владелец пользуется Obsidian на Mac, PC и iPhone. Существующие решения (remotely-save) дают три боли: конфликты, долгая синхронизация, «разъезжание» хранилищ между устройствами. Obsyncian решает это хорошо, но через своё облако с закрытым сервером. Нужен плагин, который **надёжнее и не медленнее Obsyncian**, но хранит данные **в облаке пользователя** — в приватном репозитории GitHub, зашифрованно.

GitHub выбран потому, что даёт то, чего нет у Google Drive/WebDAV: атомарную условную запись (обновление файла по sha предыдущей версии, обновление ветки только с ожидаемого коммита). Это та же гарантия «два устройства не перезапишут друг друга», на которой держится сервер Obsyncian. Плюс бесплатная история версий.

## Цели

1. Ни одна сохранённая правка не теряется: ни при гонке устройств, ни при обрыве сети, ни при потере локального состояния.
2. Все устройства сходятся к одному состоянию; истина — ветка `main` репозитория.
3. Правка доезжает до другого открытого устройства за ~3–7 с (без внешнего ускорителя).
4. Холостой синк — 1 запрос, не тратящий лимит; первая загрузка нового устройства — единицы запросов.
5. Всё, что уходит на GitHub, зашифровано паролем: содержимое и пути.
6. Работает на iOS (никакого Node API, только WebCrypto и API Obsidian).
7. Не выходит за лимиты GitHub при обычном использовании одним человеком на 3 устройствах.

## Не-цели (v1)

- Другие бэкенды (Google Drive, Яндекс WebDAV) — позже. Слой хранения изолирован в одном модуле, но абстракцию «под три бэкенда» сейчас не строим.
- Ускоритель доставки через ntfy/WebSocket — отложен владельцем.
- UI истории версий / просмотр диффов. История есть в git, восстановление вручную.
- Команда «сжать историю» (orphan-коммит + force push) — позже; в v1 только показ размера и предупреждение.
- Совместное редактирование в реальном времени, общий доступ к хранилищу другим людям.
- Синхронизация без пароля.

## Анти-цели (провал, даже если «работает»)

- Тихая потеря данных или тихое массовое удаление.
- Токен GitHub или пароль попадают в репозиторий (в т.ч. через синхронизацию `.obsidian/plugins/gitvault-sync/data.json`).
- Расшифровываемые без пароля пути или содержимое на GitHub.
- Плагин упирается в rate limit и «молча» перестаёт синхронизировать.

## Решения владельца

- **Хранилище:** только GitHub, приватный репозиторий пользователя.
- **Доступ:** GitHub App с доступом только к одному репозиторию. Две кнопки: «Создать репозиторий» и «Разрешить доступ».
- **Шифрование:** обязательное, паролем.
- **Конфликты:** как у Obsyncian. Непересекающиеся правки сливаются автоматически (3-way merge). Пересекающиеся — файл не трогается, рядом создаётся копия `Имя (conflict <устройство> YYYY-MM-DD HHmm).ext`. Никаких маркеров `<<<<<<<` в заметках.
- **Настройки `.obsidian`:** синхронизация опциональна, по умолчанию выключена.
- **Ускоритель (ntfy):** отложен.

## Онбординг

1. Настройки → «Создать репозиторий» → открывает `https://github.com/new?name=obsidian-vault&visibility=private` (параметры предзаполнения). Пользователь жмёт Create.
2. «Разрешить доступ» → открывает страницу установки GitHub App (`https://github.com/apps/<app>/installations/new`), пользователь выбирает «Only select repositories» → свой репозиторий.
3. Плагин запускает **OAuth Device Flow** GitHub App: показывает код, открывает `github.com/login/device`, опрашивает получение токена. Секрет приложения не нужен; `client_id` зашит в плагин.
4. Плагин находит репозиторий через `GET /user/installations/{id}/repositories` (если их несколько — выбор из списка).
5. Пароль:
   - репозиторий пуст → «Задайте пароль» (дважды), плагин пишет `gitvault.json` и делает первую загрузку;
   - репозиторий уже инициализирован → «Введите пароль», проверка по key-check, затем первичная загрузка с merge с локальными файлами (см. «Привязка устройства с существующими файлами»).

GitHub App (регистрируется один раз владельцем): права `Contents: read & write`, `Metadata: read`; Device Flow включён; без webhook. Обновление refresh-токена у GitHub App требует `client_secret`, который нельзя зашивать в публичный плагин, поэтому в настройках приложения **отключается истечение user-to-server токенов** (Optional features → User-to-server token expiration → opt out). Токен бессрочный до отзыва; на 401 плагин ставит синк на паузу «войдите снова», не теряя локальное состояние. *(Решение Claude; проверить актуальность опции при регистрации приложения.)*

Токены хранятся **только локально** (`app.saveLocalStorage` / `loadLocalStorage`, не в `data.json`), чтобы никакая синхронизация `.obsidian` не унесла их. Там же — пароль (по выбору пользователя: «запомнить на этом устройстве», по умолчанию да; иначе спрашивать при запуске) и `deviceId`.

## Формат репозитория

```
gitvault.json            # открытый: { format: 1, kdf: {...salt, iterations}, kcv }
f/ab/abcdef…             # один зашифрованный файл хранилища на путь
```

- **Имя файла** = `token(path)` — детерминированный ключевой PRF пути (как `pathToken` в Obsyncian `codec.ts`): одинаковый путь → одинаковое имя на всех устройствах, без ключа ничего не раскрывает. Шардирование по первым 2 hex-символам.
- **Содержимое файла** = base64-текст от `MAGIC "GVS1" | iv(12) | AES-256-GCM(header + data)`, где header содержит настоящий путь (UTF-8, NFC). Base64 выбран, чтобы один формат одинаково создавался через Contents API и через Tree API с inline-контентом (тот принимает только UTF-8 строку). Цена — +33 % к размеру репозитория. *(Решение Claude.)*
- **Ключ:** PBKDF2-SHA256, 600 000 итераций, соль 16 байт из `gitvault.json` → 256-битный мастер-ключ → HKDF-SHA256 (info `gvs-enc-v1` / `gvs-mac-v1`) → ключ AES-GCM 256 и ключ HMAC-SHA256 для PRF пути (`kdf.alg = "PBKDF2-SHA256+HKDF"`; итерации проверяются в диапазоне 100 000–10 000 000). *(Решение Claude.)*
- **key-check (`kcv`):** зашифрованная известная строка — проверяет пароль без его хранения.
- Переименование = удаление старого токена + создание нового (история переименования теряется — допустимо).

Код шифрования и merge можно брать из Obsyncian (MIT, указать авторство в LICENSE/NOTICE). Код из `pro/` remotely-save (PolyForm Strict) — **не использовать**.

## Локальное состояние (на устройстве, не синхронизируется)

Файл в папке плагина (`.obsidian/plugins/gitvault-sync/state.json`, исключён из синхронизации):

- `headSha` — коммит `main`, с которым устройство последний раз сошлось;
- `refEtag` — для условного опроса;
- по каждому пути: `token`, `blobSha` (git sha файла на GitHub при последнем синке — он же **база** для 3-way merge, её содержимое всегда достаётся с GitHub по sha), `localHash` (sha256 открытого текста на диске), `mtime`, `size`.

Состояние — кэш, а не истина. Потеря → пересборка (см. ниже), без потери данных.

## Цикл синхронизации

Один цикл одновременно (мьютекс); повторный запрос во время цикла ставит флаг «ещё раз».

1. **Опрос:** `GET /repos/{o}/{r}/git/ref/heads/main` с `If-None-Match: refEtag`. 304 → удалённых изменений нет.
2. **Локальное сканирование:** `vault.getFiles()` (+ `.obsidian` при включённой опции, через `adapter.list`), фильтр игнора; перехэшировать только файлы с изменённым `mtime`/`size`. Изменённые относительно `localHash` → локальные правки.
3. **Pull** (если ветка сдвинулась): `GET /git/trees/{newHead}?recursive=1` (1 запрос) → сравнить blob sha по токенам с локальным состоянием → для изменённых скачать blob (`GET /git/blobs/{sha}`), расшифровать, применить:
   - локально не меняли → записать на диск;
   - меняли с обеих сторон → **merge** (ниже);
   - удалён на GitHub, локально не меняли → удалить локально (в корзину Obsidian `vault.trash`);
   - удалён на GitHub, локально меняли → правка побеждает, файл пушится заново.
   Если изменённых файлов > N (порог, напр. 300) — вместо поштучных blob скачать tarball `GET /tarball/{sha}` (распаковка: DecompressionStream gzip + свой мини-парсер tar; если DecompressionStream нет — поштучно).
4. **Push** локальных правок:
   - 1–K файлов (K≈5) → `PUT /contents/{f/xx/token}` по одному, с `sha` = известный `blobSha` (для нового файла без sha). Это 1 запрос на правку и условная запись на уровне файла.
   - больше K → Git Data API: `POST /git/trees` (base_tree = head, inline content, чанками по размеру запроса) → `POST /git/commits` → `PATCH /git/refs/heads/main` с `force: false`.
   - удаление → `DELETE /contents/...` с `sha` (или удаление записи в tree при пакетном пути).
   - Ответ 409/422 «sha не совпадает» / ref не fast-forward → вернуться к шагу 3 для этих файлов (pull, merge, повтор). Не более 3 повторов за цикл.
5. Обновить `headSha`, `refEtag`, записи состояния. Состояние пишется атомарно (временный файл + rename через adapter) после каждого успешного шага, чтобы обрыв на iPhone не откатывал прогресс.

**Что считается изменением.** Сравнение всегда по-файловое: `blobSha` токена в дереве vs `blobSha` в состоянии. `headSha` нужен только чтобы понять «ветка сдвинулась» — поэтому собственные push (после которых `blobSha` уже обновлён из ответа) при следующем pull не выглядят как удалённые изменения, а чужие коммиты, вклинившиеся между нашими PUT, не теряются. Токен есть в состоянии, но нет в дереве → удалён на GitHub; файл есть в состоянии, но нет на диске → удалён локально.

**Регистр имён.** Mac/Windows нечувствительны к регистру, iOS — по-разному. Два удалённых пути, отличающихся только регистром, на нечувствительной ФС: второй сохраняется как конфликт-копия. *(Решение Claude.)*

**Перед любой записью на диск** файл перехэшируется; если он изменился с начала цикла (пользователь печатает), запись этого файла откладывается до следующего цикла. Для открытой в редакторе заметки используется `vault.process`.

## Merge и конфликты

Берётся `merge.ts` Obsyncian (node-diff3):

- `.md`, `.txt`: `merge3(base, local, remote)` — построчно, затем по словам для пересекающихся строк; одинаковые правки на обеих сторонах сливаются. Успех → результат пишется на диск и пушится. Неуспех → конфликт-копия.
- `.json` в `.obsidian` (при включённой опции): `mergeJson` по ключам, при споре — удалённое значение.
- Остальное (бинарники, `.canvas`, файлы > 2 МБ): конфликт-копия.
- **Нет базы** (новое устройство, файл создан на двух устройствах одновременно): идентичны → ничего; иначе — конфликт-копия. *(Решение Claude: без union-merge, проще и предсказуемее при выборе «копии».)*

**Конфликт-копия:** удалённая версия занимает исходный путь (она уже согласована с другими устройствами), локальная версия сохраняется как `Имя (conflict <имя устройства> YYYY-MM-DD HHmm).ext` и синхронизируется как обычный новый файл. Уведомление (Notice) + счётчик в статус-баре. Имя устройства задаётся в настройках, по умолчанию — платформа.

## Скорость и лимиты GitHub

Ограничения (по документации GitHub, проверить при реализации): основной лимит 5000 запросов/ч на пользователя; вторичный — не более 80 запросов создания контента в минуту и 500 в час; файл ≤ 100 МБ; рекомендуемый размер репозитория ≤ 1 ГБ (жёстко ~5 ГБ). Условные запросы с ответом 304 не тратят основной лимит.

- **Push:** через 2 с после последней правки; при непрерывном наборе — не реже раза в 15 с. Клиентское «ведро токенов» на записи (напр. ёмкость 20, пополнение 4/мин на устройство); при опустошении интервал растёт. 403/429 → уважать `Retry-After`/`x-ratelimit-reset`, показать статус «пауза до HH:MM», не повторять вслепую.
- **Опрос:** каждые 4 с, пока окно активно (`document.visibilityState === "visible"`); каждые 60 с в фоне (десктоп); мгновенно при возврате в приложение и при открытии. Если 304 всё-таки тратит лимит — увеличить интервал (проверить на практике).
- **Первая загрузка хранилища:** пакетный путь Tree API, чанки до ~20 МБ на запрос (реальный предел размера запроса замерить).
- **Первая загрузка нового устройства:** tarball одним запросом.
- **Размер:** показывать размер репозитория (`GET /repos/{o}/{r}` → `size`) в настройках; предупреждение при 700 МБ. Файлы > 50 МБ не синхронизируются, с предупреждением (base64 + лимит 100 МБ).

## Предохранители

- **Массовое удаление:** если цикл собирается удалить локально или на GitHub > 20 % файлов (и > 10 штук) — стоп, модалка «подтвердить / отменить». Порог настраивается.
- **Пустое хранилище:** если локально 0 файлов, а на GitHub много (или наоборот) — никогда не трактовать как «всё удалили»; трактовать как первичную загрузку.
- **Неверный пароль / смена `gitvault.json`:** синк останавливается с понятной ошибкой.
- **Игнор всегда:** `.obsidian/plugins/gitvault-sync/` целиком, `.obsidian/workspace*.json`, `.trash/`, файлы конфликтов не исключаются (они обычные файлы).

## Привязка устройства с существующими файлами / пересборка состояния

Состояния нет, а файлы локально есть: скачать дерево и все blob (tarball), для каждого пути:
- содержимое совпадает → просто записать состояние;
- отличается → поискать базу в истории файла (`GET /commits?path=f/xx/token`, ограничить 20 коммитами): если какая-то прошлая версия совпадает с локальной — значит, локально просто устаревшая копия, взять удалённую без конфликта; иначе — конфликт-копия.
- есть только локально → push; есть только на GitHub → скачать.

## Синхронизация настроек (опция)

Включается тумблером «Синхронизировать настройки и плагины». Включает `.obsidian/**` кроме игнора выше. На каждом устройстве свой тумблер. JSON мержится по ключам. Изменения настроек применяются после перезапуска Obsidian (уведомление).

## Тестирование

- Модульные: шифрование (кругом, неверный пароль, порча байта → отказ), merge (взять тесты Obsyncian `merge.test.ts`), tar-парсер.
- **Симуляция:** фейковый GitHub в памяти с настоящей семантикой sha-CAS, ref fast-forward, 409/422, вторичным лимитом и задержкой видимости; 3 фейковых устройства с фейковым vault; случайные создания/правки/удаления/переименования и обрывы в случайных точках цикла; после прогона — все устройства сходятся, и **каждая версия, которую пользователь когда-либо сохранил последней на устройстве, присутствует** либо в итоговом файле, либо в конфликт-копии, либо в истории git. Тысячи прогонов с seed.
- Ручной e2e на реальном приватном репозитории (Mac + iPhone) перед релизом.

## Риски

1. Новый код синхронизации — главный риск; закрывается симуляционными тестами.
2. Рост репозитория у хранилищ с большим количеством медиа — v1 предупреждает, сжатие истории — позже.
3. Требуется регистрация GitHub App владельцем (client_id в сборке).
4. Вторичные лимиты GitHub могут измениться — обработка 403/429 обязательна, не только клиентское ведро.
